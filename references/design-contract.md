# Точная фиксация выбранного дизайна

Читать после выбора нового направления, перед реализацией и после возобновления задачи. Для точной правки существующего проекта использовать текущую систему; не требовать заполнения пустой новой схемы и повторного выбора. При необходимости перенести известные решения в контракт, сохранив источники; неизвестное не объявлять одобренным.

## Один источник решений

`.absolute/DESIGN.md` содержит понятное объяснение и историю. `.absolute/design-contract.json` — минимальные проверяемые сведения; взять шаблон из `templates/design-contract.json` этого навыка **по необходимости**, не создавать для обычного разговора. Читаемые описания и контракт не должны противоречить друг другу. Генерируемый каталогом MASTER.md — исследовательский материал, пока явно не включён в выбранную систему.

Заполнить:
- `scope`: `product` для реального проекта, `test-fixture` только для испытания.
- `selected_option`, `status`, `approval`: точная цитата выбора, относительный файл записи ответа, происхождение `user` или `test-harness`. Файл/поле не доказывает подлинность само по себе: сверить с реальным сообщением; не создавать цитату из своего предложения.
- `artifacts`: пути от корня проекта и SHA-256 согласованных текстов, токенов, выбранной пробы/контрольных изображений. Фиксировать только нужные источники, не каждый файл реализации. Шрифты/ассеты включать по важности и доступности прав.
- `rules`: композиция и её изменение на узком экране; точные шрифты/роли/наличие нужных символов; цвета; сетка/интервалы; ключевые компоненты и состояния; поведение движения и reduced motion; разрешённый контент. Для неприменимого раздела записать причину, а не придуманные значения.
- `checks`: несколько наблюдаемых важных требований: текст или вычисленное CSS-свойство конкретного селектора, размер окна, состояние. Привязать их к согласованному правилу; не проверять ради количества.

Пути локальные и внутри проекта; не включать ключи, приватные URL и чужие пользовательские данные. Доступные названия управления, обязательные ошибки/предупреждения сохраняются; не блокировать их ради буквального запрета новых строк. Нужные служебные тексты фиксировать при согласованной реализации и проверять по назначению.

## Происхождение: контракт v2

Новый контракт использует schema_version=2 и непустой `design_provenance`. Каждая запись имеет `kind`, `detail` (конкретные заимствованные признаки/адаптация), `applies_to` (поля rules), `evidence` с локальными path/sha256. Все восемь полей rules должны иметь происхождение; неприменимый motion, например, можно обосновать выбранным статичным материалом. Контент берётся из утверждённого брифа через existing-approved с записью выбора, а не из рекламного демо.

- `registry`: source_id из design-source-registry.json, точный HTTPS URL разрешённого сайта, `element` (реальный компонент/экран/иконка/шрифт). Для GitHub допускается только указанный репозиторий, не любой github.com.
- `bundled`: source_id включённого дизайн-навыка, `element` с точным файлом/разделом/ID материала.
- `existing-approved` или `user-exception`: `approval_record` с локальным сообщением пользователя и точная `approval_quote`; использовать для утверждённого проекта, контента брифа или прямо выбранного нового источника.

Доказательство — фактический локальный снимок/исходник/заметка просмотренного материала, в допустимом объёме. Хеш не удостоверяет истинность происхождения и запись ответа не удостоверяет волю человека; их нельзя фабриковать. Старый реальный v1-контракт дополнить происхождением из сохранённых решений без смены дизайна или повторного интервью; реальный продукт без provenance не проходит checker. Учебные v1 fixtures сохраняют прежнюю совместимость. Для нового реального проекта всегда v2.

## Перед реализацией

`python3 <skill-directory>/scripts/design_check.py --project <project-root> --stage ready`

Скрипт проверяет поля, наличие файлов, хеши и различие реального/тестового выбора. Он не подключается к модели, не управляет инструментами и не удостоверяет волю пользователя. Нельзя заполнять поля ложным одобрением ради успешного выхода. Пока readiness не пройден, исправлять сведения или выяснять отсутствующий выбор; независимая работа разрешена.

## После реализации

В доступном браузере получить фактические значения `checks` на указанных размерах/состояниях и снимки. Записать `.absolute/observed-design.json`: `contract_sha256` текущего контракта, `checks` как список `{id, actual}` и `evidence` как список `{path, sha256, description}` с реальными локальными материалами проверки. Не переписывать expected в actual без измерения. Для динамического текста/состояния выбрать устойчивое точное наблюдение, а не широкую догадку.

`python3 <skill-directory>/scripts/design_check.py --project <project-root> --stage verify`

Совпадение автоматических значений — только часть приёмки. Обязательно самостоятельно открыть снимки/предпросмотр, сравнить с выбранной пробой, проверить композицию, шрифт, переносы, контент и ключевые действия. Записать вывод и ограничения в VERIFICATION. Если просмотр недоступен, `needs-visual-check`; JSON с совпадениями не даёт права написать «визуально проверено».

## Изменения и новый чат

До точной правки прочитать STATE/BRIEF/DESIGN и контракт. Менять только запрошенное, сохраняя остальные решения. Внести изменение в соответствующее правило/токен/check и приложить реальную новую цитату/запись запроса. Сохранить предыдущий контракт в журнале версий перед изменением. Не обновлять хеши автоматически, чтобы скрыть случайную смену стиля. После изменения контракта старые observations устарели; измерить заново. При конфликте между контрактом и текущим продуктом сначала определить причину, а не принять продукт за новый эталон.

## Исправление 0.9: конкретный макет и раздельная приёмка

Применять [visual-quality.md](visual-quality.md): generic styles/palettes/component docs не являются основанием новой композиции. Для v2 (включая новые test-fixtures) нужен visual_basis с настоящим source capture и разбором признаков. Проверка verify также требует visual-review.json с wide/narrow сравнением выбранной пробы и реализации. Синтетическое одобрение не подтверждает эстетическое качество; отклонённое пользователем направление сохранять в истории как rejected.

Legacy v1 test fixtures проверяются только с явным `--allow-legacy-fixture`; для новых симуляций это не разрешено. Captures должны быть структурно целыми PNG/JPEG/WebP; размеры wide/narrow совпадают с viewport. Checker не декодирует пиксели и не удостоверяет происхождение скриншота: разные пути и совпадающие хеши не доказывают запуск браузера. Реальный просмотр и независимая запись действий обязательны; идеальное совпадение пикселей допустимо. Для explicitly-selected deviation требуются reason и цитата/запись выбора.

## Концептуальная готовность (1.0)
Для нового продукта оставить product_concept_required=true в шаблоне: design_check ready/verify дополнительно проверяет выбранный concept-plan.json. Для точной правки существующего интерфейса без нового продукта этот этап не навязывается; не придумывать исследование задним числом. Для нового UI по уже выбранной концепции перенести существующее решение с реальным основанием. Поле не является блокировщиком инструментов и не доказывает пользу/подлинность выбора.

Для точной правки исторического проекта не требовать миграцию всех незатронутых решений или полного нового исследования. Обновить затронутые сведения и обязательный журнал, проверить фактическую правку. Если старый контракт не проходит новые общие требования, честно записать ограниченную проверку; не утверждать полный PASS. Полный новый контракт обязателен для нового продукта/нового направления.
