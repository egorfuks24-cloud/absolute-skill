# Проверка результата

Перед сдачей сверить изменённую область с BRIEF и DESIGN. Проверить:

- Нет новых не согласованных текстов, демонстрационных показателей и декоративных блоков.
- Композиция, шрифты, материалы и движение имеют записанное основание; библиотечный демостиль не проник в продукт.
- Референс действительно был открыт и изучен. При его недоступности сравнение не объявляется выполненным.
- Предпросмотр открыт на широком и узком экране; проверены изменённые состояния, загрузка/ошибки при применимости, клавиатура, видимый фокус, касания при доступности.
- Для движения проверены повторный запуск, прерывание, конечное состояние и reduced motion. Производительность описывается по наблюдению/измерению, не по обещанию библиотеки.
- Функциональные проверки соответствуют риску изменения. Не создавать тесты, которые лишь повторяют строки реализации.

В `.absolute/VERIFICATION.md` указать дату, проверяемую версию/коммит при наличии, способ, размер экрана, результат, исправления и непроверенное. Статус `verified` допустим только при завершённых применимых проверках. Если UI нельзя посмотреть — `needs-visual-check`, даже при успешной сборке.

Проверка самого Absolute Skill имеет отдельные уровни: структура/пути, работа утилит, статический анализ безопасности, сценарная проверка инструкций и реальное поведение модели в чистой сессии. Не подменять последний уровень первыми четырьмя.

Для UI с новым выбранным направлением применять design-contract.md: хеши согласованных материалов, фактические наблюдения и отдельный визуальный просмотр. Автоматическое совпадение отдельных свойств не подтверждает композицию или качество целого. Старое наблюдение не подходит к изменённому контракту.

Для разработки приложения включить проверку по application-security.md. Проверка навыков не заменяет проверку продукта.

## Исправление 0.9: конкретный макет и раздельная приёмка

Применять [visual-quality.md](visual-quality.md): generic styles/palettes/component docs не являются основанием новой композиции. Для v2 (включая новые test-fixtures) нужен visual_basis с настоящим source capture и разбором признаков. Проверка verify также требует visual-review.json с wide/narrow сравнением выбранной пробы и реализации. Синтетическое одобрение не подтверждает эстетическое качество; отклонённое пользователем направление сохранять в истории как rejected.


Перед фиксацией пробы и сдачей применять [content-quality.md](content-quality.md): отдельный реестр текста и проверка объектов. Совпадение с пробой не исправляет её исходные дефекты.


## Основной опыт продукта (1.0)
Для нового продукта сначала product-discovery.md и concept-development.md. Варианты различаются механикой/первым сценарием, затем визуальными решениями. Проба показывает вход, действие и результат, а не одну обложку. До сдачи outcome-evaluation.md; документы и технический PASS не подтверждают интерес и пользу. Точная правка готового продукта не запускает новый концептуальный этап.
