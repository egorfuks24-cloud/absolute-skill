# Визуальное основание и честная приёмка

Читать после ответов на новый визуальный бриф, до проб. Выбор пользователя и прямой референс имеют приоритет. Это исправление продемонстрированного обхода: general Swiss + palette row + own simulated approval produced a generic dashboard despite valid provenance.

## Основание композиции

Каталог ui-ux-pro-max, палитра, шрифт, философия Emil и документация компонента помогают реализации; сами по себе они не являются макетом нового проекта. Нельзя собрать привычный hero/sidebar/cards и оправдать его строкой Swiss, LMS или названием HeroUI. Если поиск выдал неподходящее — признать это, не выбирать ту же типовую сетку вручную.

Для каждого нового направления открыть и визуально изучить конкретный экран/композицию из разрешённого пула либо явно выбранный пользовательский макет. Сохранить PNG/JPEG/WebP-снимок с точным URL/названием экрана и короткую запись изучения. Зафиксировать минимум два наблюдаемых признака: масштаб/место ключевого визуала, расположение текста/управления, характер типографики, материал/цвет, пространство, выбранный эффект. Записать, что берём, как адаптируем под сценарий, что не копируем. Код и чужие ассеты не переносить без проверки прав. Снимок нужен для локального анализа, не как ассет продукта или массовая копия каталога.

Иконка, шрифт и эффект не задают композицию страницы. Общий style/palette CSV не проходит как primary reference. Источники новых композиционных референсов: Astryx, ArloUI, posts.design, recent.design, Inspora, 21st.dev; конкретный явно выбранный макет/существующий интерфейс допускается через существующее approval. Остальные источники работают для своей роли: иконки, шрифты, движение. Конкретный визуальный материал вложенного навыка можно показать пользователю как макет; его явный выбор записать с actual visual capture через existing-approved, без притворного одобрения каталога агентом.

## До выбора

Показать две-три визуально различные пробы на одинаковом содержании, не перекрашивания одной сетки. Проба — реальное ключевое состояние, не только таблица характеристик. Для каждой — исходный визуальный материал и заимствованные признаки. Не встраивать кабинет/лендинг по привычке, если исходная идея требует другой сценарий. Сложность, оценка стоимости и потребность в AI не разрешают агенту молча урезать нужный продукт до удобного пустого MVP. Если это симуляция, проговорить существенные границы в вымышленном диалоге и не выдавать их за требования настоящего пользователя.

Контракт v2 требует visual_basis: provenance_index, material_type (specific-composition / approved-mockup / existing-interface), capture {path,sha256}, inspection {path,sha256}, borrowed_features (минимум два), adaptation. Путь и хеш обязаны соответствовать фактически просмотренному материалу. Checker проверяет структуру/связи/формат, не подлинность просмотра и не вкус. Самостоятельно созданную пробу нельзя назвать внешним reference capture.

## После реализации

Функции, безопасность и дизайн — отдельные выводы. PASS проверки кнопок не свидетельствует об эстетическом качестве. Сравнить настоящие wide/narrow снимки реализации с выбранными пробами: масштаб, положение, типографика и переносы, интервалы, материалы, контент, главный визуальный приём. Случайные сдвиги исправить. Намеренное существенное отклонение требует выбора; не оправдывать дрейф записью natural wrapping и не обновлять эталон под результат.

Записать .absolute/visual-review.json: contract_sha256, status=reviewed, comparisons. Каждая comparison: viewport, reference {path,sha256} из выбранных артефактов, actual {path,sha256} из observed evidence, retained_features (конкретные наблюдения), deviations (пустой список либо записи status=fixed / explicitly-selected с основанием). Нужны wide>=1000 и narrow<=600; сами картинки просмотреть. Agent review — не человеческое одобрение и не универсальное доказательство уникальности.

## Симуляция

По прямому поручению допустим synthetic test-harness выбор, как прежде. Он не разрешает себе придумать довольного заказчика и затем объявить хороший дизайн подтверждённым. В симуляции visual-review.aesthetic_acceptance=synthetic-only; итог говорит «работающий прототип, визуальная оценка пользователем ещё не получена». Никакого обещания «запрет гарантированно исключил slop» по заполненному JSON. Реальный отрицательный отзыв фиксируется как rejected, прежняя проба не остаётся approved для следующего редизайна. Сохранять историю, не переписывать провал как успех.

## Продолжение и исключения

Точная правка сохраняет имеющийся выбранный дизайн. Для старого v2-контракта добавить visual_basis из сохранённых настоящих макетов/снимков, не проводить новый дизайн ради обновления схемы. Если подтверждение/изображение потеряно — продолжать независимую работу, восстановить его до зависимой реализации. Legacy v1 test-fixture остаются совместимыми; реальные продукты и новые v2 fixtures проходят новый gate.

Legacy v1 test fixtures проверяются только с явным `--allow-legacy-fixture`; для новых симуляций это не разрешено. Captures должны быть структурно целыми PNG/JPEG/WebP; размеры wide/narrow совпадают с viewport. Checker не декодирует пиксели и не удостоверяет происхождение скриншота: разные пути и совпадающие хеши не доказывают запуск браузера. Реальный просмотр и независимая запись действий обязательны; идеальное совпадение пикселей допустимо. Для explicitly-selected deviation требуются reason и цитата/запись выбора.


Перед фиксацией пробы и сдачей применять [content-quality.md](content-quality.md): отдельный реестр текста и проверка объектов. Совпадение с пробой не исправляет её исходные дефекты.
